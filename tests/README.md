# Тесты «Русские шашки»

Набор проверок, защищающих места, где в этом проекте уже случались
реальные баги. Цель — не процент покрытия, а воспроизводимая защита от
повторения известных поломок.

## Быстрый старт

```bash
npm ci        # нужен: часть наборов требует devDependencies
npm test      # основной набор (node tests/run.js)
```

`npm test` печатает итоговое количество пройденных проверок — это и
есть актуальное число. Здесь оно намеренно не зафиксировано: набор
растёт почти с каждой задачей, и любая записанная цифра устаревает
быстрее, чем документация.

## Команды

| Команда | Что делает |
|---|---|
| `npm test` | Основной набор из `tests/run.js` |
| `npm run check` | `node --check script.js` — только синтаксис клиента |
| `npm run test:browser` | Layout в Chromium и WebKit, **в `npm test` не входит** |
| `npm run test:rules` | Firebase Rules через настоящий Emulator |
| `node --test tests/worker/*.test.mjs` | Все наборы Worker'а |
| `node --check worker/index.mjs` | Синтаксис Worker'а |

npm-скрипта для Worker'а нет — используется прямая команда выше.
Отдельного скрипта для settlement тоже нет: `settlement-behavior.test.js`
зарегистрирован в `tests/run.js` и запускается вместе с `npm test`
(backend CI дополнительно вызывает его напрямую).

### Требования среды

`package.json` фиксирует минимум: `engines.node: ">=20"`. CI использует
Node 20 для клиентских тестов и Node 22 для backend.

Для `npm run test:rules` дополнительно нужны **Java** (CI берёт 21) и
`firebase-tools` из devDependencies, то есть предварительный `npm ci`.
При первом запуске Emulator скачивает свой jar — без доступа в сеть
команда не отработает.

## Основной набор (`tests/run.js`)

Больше сорока наборов; перечислять их поимённо здесь бессмысленно —
список живёт в самом `tests/run.js`. По смыслу они делятся так:

- **Правила и движок** — базовые правила русских шашек, общий движок,
  guard'ы движка, ничьи (пороги, взаимодействие правил, жизненный цикл
  draw-полей и round-trip через Firebase).
- **Комнаты, приглашения, лобби** — создание комнат и обработка
  отказов, вход по ссылке, гонки при входе, приватность приглашений,
  рендер лобби, слушатели зрителей, очистка комнат.
- **Presence и переподключение** — жизненный цикл присутствия,
  reconnect, сценарий «оба офлайн».
- **Elo и рейтинговые партии** — источник рейтинга на клиенте,
  поведение settlement, атрибуция реванша, порядок draw-событий,
  бюджет сложности Rules, UI рейтинга и таблицы лидеров.
- **Вход и надёжность клиента** — auth-gate, стартовая заставка,
  синхронизация ходов, часы, обработка отказов при ходе владельца.
- **UI-регрессии** — кнопка «Назад», панели игроков, стек взятых шашек.
- **Guard'ы** — классификация ошибок App Check, i18n пользовательских
  строк, отсутствие удалённого мёртвого кода, самопроверка самого
  раннера.

### Как устроены тесты

Наборы работают с продакшен-файлами, а не с копиями, но двумя разными
способами:

- **Поведенческие** извлекают функции **из настоящего `script.js`** по
  имени (через `tests/helpers/loader.js` либо собственной inline-
  экстракцией) и выполняют их с моками Firebase и DOM.
- **Guard-наборы** читают исходник напрямую и проверяют по нему
  инварианты, ничего не исполняя: например, что символ удалён, что код
  ошибки не попал в определённый список, что строка локализована.

№40: если инвариант про CSS-геометрию (точный `px`/`em`/`clamp`) можно
проверить рендером — он живёт в браузерном наборе, а не regex'ом по
исходнику CSS. Source-тесты фиксируют структуру (что элемент существует,
как устроена разметка), не то, сколько он занимает пикселей на экране.

Общее следствие: наборы **привязаны к именам функций и к тексту
исходника**. Переименование функции в `script.js` уронит тесты — это
ожидаемое поведение, а не дефект.

### Интеграционное исключение

`back-button.test.js` вызывает **настоящую** `renderPlayerPanels()`
внутри **настоящей** `renderBoard()`.

Это принципиально. Ранее существовала версия теста, которая заглушала
`renderPlayerPanels` — она показывала «всё зелено», пока игрок на
реальном телефоне видел две кнопки «Назад», а зритель — ни одной. Баг
жил именно во взаимодействии двух функций.

**Не заглушайте `renderPlayerPanels` в этом тесте.**

## Браузерный набор

```bash
npm ci
npx playwright install --with-deps chromium webkit
npm run test:browser
```

`panel-browser-layout.test.js` меряет раскладку панели в **настоящих**
движках — Chromium и WebKit — на ширинах 320/360/390/430. Playwright
теперь обычная devDependency проекта, а движки ставятся отдельной
командой выше (сотни мегабайт, поэтому не при каждом `npm ci`).

Набор **fail-closed**: движки импортируются жёстко и ошибка запуска не
перехватывается. Отсутствующий пакет, неустановленный движок и упавшая
проверка одинаково дают ненулевой код возврата. Раньше здесь был
try/catch, печатавший «ИТОГ: 0/0» с кодом 0 — то есть непроведённая
проверка выглядела как успешная; для CI это неприемлемо.

**WebKit — не iPhone.** Это ближайшее автоматизируемое приближение к
Safari, но Telegram на iOS использует системный WKWebView со своим
viewport, клавиатурой и жестами. Ручной smoke на реальном устройстве
этот набор не заменяет.

`panel-browser-layout.test.js` — единственный **корневой**
`tests/*.test.js`, намеренно не зарегистрированный в `tests/run.js`.
Наборы в подкаталогах `tests/worker/` и `tests/firebase-rules/` в
runner тоже не входят и запускаются своими командами (см. разделы
«Worker» и «Firebase Rules»).

## Firebase Rules (Emulator)

```bash
npm run test:rules
```

Правила лежат в репозитории: `firebase/database.rules.json`. Наборы
`tests/firebase-rules/database.rules.test.mjs` и
`rated-events.rules.test.mjs` прогоняются против **настоящего**
Database Emulator через `@firebase/rules-unit-testing`, а не против
мока.

Важно различать два уровня:

- клиентские наборы из `npm test` используют **мок** Firebase — они
  проверяют, что и в каком порядке клиент пытается записать;
- наборы Rules Emulator проверяют, **пропустят ли правила** такую
  запись.

Emulator при этом не моделирует production-проект целиком: реальные
задержки, сеть, App Check и поведение конкретных клиентских SDK
остаются за его пределами.

## Worker

```bash
node --test tests/worker/*.test.mjs
```

Покрывают rated-replay, приём событий, обновление имени в таблице
лидеров, fail-closed и backoff App Check, лимит размера тела запроса.

> **CI coverage note.** `backend.yml` сейчас вызывает Worker-наборы
> явным списком — только `worker-unit.test.mjs` и
> `rated-replay-unit.test.mjs`. Остальные файлы в `tests/worker/`
> в этот workflow пока не подключены, и до отдельной правки workflow
> их нужно прогонять локально командой выше.

## CI

**`tests.yml`** (Node 20) — `npm run check`, затем `npm test`. Ни
браузерный набор, ни Worker, ни Rules Emulator сюда не входят.

**`browser.yml`** (Node 20) — `npm ci`, установка движков
(`npx playwright install --with-deps chromium webkit`), затем
`npm run test:browser`. Отдельный workflow, чтобы не утяжелять основной
прогон загрузкой движков.

**`backend.yml`** (Node 22, Java 21) — `npm ci`, затем:

```bash
node --check worker/index.mjs
node --test tests/worker/worker-unit.test.mjs tests/worker/rated-replay-unit.test.mjs
node tests/settlement-behavior.test.js
npm run test:rules
```

Обратите внимание на вторую строку: это **не** тот же набор, что
локальная команда `node --test tests/worker/*.test.mjs` — CI перечисляет
два файла поимённо (см. заметку в разделе «Worker»). Третья строка
дублирует settlement, который уже входит в `npm test` через
`tests/run.js`.

## Проверка, что тест не «пустой»

Тест полезен, только если он падает на сломанном коде. Основной набор
умеет работать против другой версии клиента:

```bash
TARGET_SCRIPT=/путь/к/сломанному/script.js node tests/run.js
```

Тот же приём применим точечно: временно внести правку, обратную
проверяемой, и убедиться, что падает именно ожидаемая проверка. Если
тест остаётся зелёным — он ничего не гарантирует, и чинить нужно тест,
а не код.

## Чего эти тесты не проверяют

- **Реальные сеть, задержки и гонки между устройствами** не
  моделируются: моки синхронны, Emulator локален.
- **Атомарность между двумя устройствами** — каждый клиент пишет свою
  запись; расхождение «у одного поражение, у второго нет победы»
  тестами не закрывается.
- **Визуальный слой** — CSS, вёрстка, реальные размеры на телефоне
  (браузерный набор проверяет только layout-инварианты).
- **Сила ИИ** — проверяется отсутствие падений, не качество игры.
- **Production Firebase и Cloudflare** — Rules проверяются Emulator'ом,
  Worker — юнит-тестами с моками сети; сам развёрнутый бэкенд ни один
  набор не трогает.

## Соглашение

Тесты **не должны** править продакшен, чтобы стать зелёными. Если тест
требует изменения `script.js` — сначала выясните, кто неправ. При
подготовке набора несколько проверок падали именно из-за ошибок в самих
тестах и исправлялись тесты, а не движок.
