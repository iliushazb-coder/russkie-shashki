# Regression-тесты «Русские шашки»

Минимальный набор проверок, защищающих те места, где в этом проекте
уже случались реальные баги. Цель — не «покрытие ради процента», а
воспроизводимая защита от повторения известных поломок.

## Как запустить

```bash
npm test
```

или напрямую:

```bash
node tests/run.js
```

**Зависимостей нет.** `npm install` можно не выполнять — используется
только стандартный Node (проверено на Node 18+). Именно поэтому в
`package.json` нет секции `dependencies`.

Дополнительно доступна быстрая проверка синтаксиса продакшена:

```bash
npm run check    # node --check script.js
```

## Что проверяется

| Файл | Область |
|---|---|
| `online-stats.test.js` | Запись онлайн-статистики: оптимистичное состояние, retry, маркер партии, реванш |
| `back-button.test.js` | **Интеграционный.** `renderBoard()` + `renderPlayerPanels()` вместе, видимость кнопок |
| `draw-rules.test.js` | Автоматические ничьи: пороги, материальные условия, сброс счётчиков |
| `draw-interaction.test.js` | Взаимодействие правил ничьей между собой, порядок срабатывания |
| `draw-state-lifecycle.test.js` | Жизненный цикл draw-полей + serialize/deserialize/Firebase round-trip |
| `core-rules.test.js` | Базовые правила русских шашек 8×8 |

## Как устроены тесты

Тесты извлекают функции **из реального `script.js`** по имени
(`tests/helpers/loader.js`) и выполняют их с моками. Это сделано
намеренно: тесты работают с продакшен-файлом, а не с копией, поэтому
ломаются, если продакшен изменится несовместимо.

Обратная сторона: тесты **привязаны к именам функций**. Переименование
функции в `script.js` уронит тесты — это ожидаемое поведение, а не
дефект.

### Интеграционные тесты

`back-button.test.js` — единственный по-настоящему интеграционный: он
вызывает **настоящую** `renderPlayerPanels()` внутри **настоящей**
`renderBoard()`.

Это принципиально. Ранее существовала версия теста, которая заглушала
`renderPlayerPanels` — она показывала «всё зелено», пока на реальном
телефоне игрок видел две кнопки «Назад», а зритель — ни одной. Баг жил
именно во взаимодействии двух функций.

**Не заглушайте `renderPlayerPanels` в этом тесте.**

## Что эмулируется моками

- **Firebase** — `database.ref().transaction()/set()/update()/remove()/on()`
  заменены на объекты в памяти. Проверяется логика клиента: что и в
  каком порядке он пытается записать.
- **DOM** — кнопки, модалки, элементы доски.
- **Telegram WebApp** — не используется.

## Чего эти тесты НЕ проверяют

Важно не создавать ложного впечатления:

- **Реальные Firebase Security Rules не проверяются.** Мок принимает
  любую запись. Тест «клиент отправил такую-то запись» ≠ «Rules её
  пропустят». Rules живут в консоли Firebase и в репозитории
  отсутствуют.
- **Атомарность между двумя устройствами не проверяется.** Каждый
  клиент пишет только свою запись `stats/<uid>`; ситуация «у одного
  поражение, у второго нет победы» существует в архитектуре и тестами
  не закрывается.
- **Реальная сеть, задержки, гонки между устройствами** — не
  моделируются.
- **Визуальный слой** — CSS, вёрстка, реальные размеры на телефоне.
- **AI-сила** — тесты проверяют отсутствие падений, но не качество игры.

## Проверка, что тест не «пустой»

Тест полезен, только если он падает на сломанном коде. Прогнать набор
против другой версии файла:

```bash
TARGET_SCRIPT=/путь/к/сломанному/script.js node tests/run.js
```

Набор проверен на четырёх намеренно сломанных версиях, и каждая
ловится:

| Внесённая поломка | Провалов |
|---|---|
| Запись статистики из оптимистичного состояния + отсутствие retry | 10 |
| Маркер партии без `matchNumber` (реванш в той же комнате) | 4 |
| Возврат слепого `querySelectorAll('#game-screen .menu-button')` | 11 |
| Правило большинства при взятии (его в русских шашках нет) | 2 |

На чистой версии — 156 пройдено, 0 провалено.

## Соглашение

Тесты **не должны** править продакшен, чтобы стать зелёными. Если тест
требует изменения `script.js` — сначала выясните, кто неправ. При
подготовке этого набора восемь проверок падали именно из-за ошибок в
самих тестах (неверная сигнатура `getLegalDestinations`, неверное
представление о механизме `pendingRemovals`), и исправлялись тесты, а
не движок.
