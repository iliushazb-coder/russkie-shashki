# Русские шашки

Telegram Mini App: русские шашки 8×8. Игра с ботом, онлайн-партии вдвоём,
режим зрителя, рейтинг Elo и таблица лидеров. Три языка: русский,
английский, итальянский.

Играть: открыть Mini App в Telegram.

## Возможности

- **Партия с ботом** с выбором сложности, полностью на устройстве.
- **Онлайн-партия по ссылке-приглашению**: создатель выбирает контроль
  времени, приглашённый занимает место чёрных одной транзакцией.
- **Лобби «Кто играет?»** — список идущих партий; в них можно зайти
  зрителем.
- **Рейтинговые партии**: Elo и таблица лидеров, результат считается на
  сервере.
- **Реванш** в той же комнате без пересоздания.
- **Присутствие и переподключение**: уход и возвращение игрока
  отслеживаются серверными метками, партия переживает сворачивание
  приложения.
- **Ничьи и технические исходы** — автоматические правила ничьей,
  предложение ничьей, сдача, поражение по времени и по отсутствию.

    фронтенд     статические HTML/CSS/JS, без фреймворков и без сборки
    данные       Firebase Realtime Database, регион europe-west1
    личность     Firebase Auth (custom token), Telegram WebApp API

## Архитектура

Клиент общается с двумя серверными сторонами:

- **Firebase RTDB** — состояние комнат, ходы, присутствие, статистика.
  Доступ ограничен Security Rules.
- **Cloudflare Worker** — вход через Telegram и всё, что связано с
  рейтингом.

### Вход

    Telegram initData
      -> POST /auth/telegram (Worker)
      -> проверка подписи бота и свежести auth_date
      -> Firebase custom token с uid вида tg_<telegram id>
      -> signInWithCustomToken на клиенте
      -> Firebase ID token
      -> заголовок Authorization для rated-эндпоинтов

Личность назначает сервер: клиент не выбирает свой uid и не берёт его из
`initDataUnsafe`. Сессия живёт только в памяти вкладки
(`Persistence.NONE`) — `auth_date` фиксируется при запуске Mini App, и
переживать перезагрузку сессии незачем. Долгую партию держит уже
обновляемый Firebase ID token, а не исходный `initData`.

### Worker API

| Endpoint | Назначение |
|---|---|
| `GET /health` | Проверка живости |
| `POST /auth/telegram` | Проверка Telegram initData, выдача custom token |
| `POST /rated/join` | Регистрация рейтинговой партии |
| `POST /rated/event` | Приём событий партии в защищённый журнал |
| `POST /rated/settle` | Подсчёт и запись результата |

Подтверждённые в исходниках контроли: проверка подписи Telegram, проверка
Firebase ID token вызывающего для rated-эндпоинтов, аллоулист источников
(CORS), потоковый лимит тела запроса 32 KiB, серверный расчёт результата и
защищённый журнал событий партии.

Ограничение частоты запросов на стороне Cloudflare — это конфигурация
развёртывания; репозиторий её не описывает и не подтверждает.

### App Check

App Check задействован с двух сторон, и это **два независимых пути**, а не
один токен, передаваемый по цепочке:

- **Клиент** активирует App Check через reCAPTCHA; заголовок к своим
  запросам в RTDB клиентский SDK добавляет сам.
- **Worker** чеканит собственный токен для своих REST-запросов в RTDB:
  подписывает OAuth-assertion ключом сервисного аккаунта, обменивает его
  на access token, вызывает Firebase App Check API, кеширует результат и
  кладёт его в заголовок `X-Firebase-AppCheck`. Голый REST, в отличие от
  SDK, заголовок сам не проставляет.

Для пути Worker→RTDB переменная `APP_CHECK_REQUIRED` включает режим
fail-closed: если токен обязателен, а получить его не удалось, запрос в
RTDB не отправляется вовсе. Повторные попытки получения токена
ограничены экспоненциальным backoff'ом.

Режим включается конфигурацией развёртывания. Репозиторий показывает, что
код это поддерживает, но не подтверждает, включён ли флаг в production.

## Рейтинговые партии

Клиент ведёт саму партию, но **не является источником истины для
рейтинга**. Ходы и значимые события уходят через `/rated/event` в
защищённый журнал, доступный на запись только серверной личности;
`/rated/settle` пересчитывает исход по этому журналу и записывает
результат. Узел `stats/<uid>` в Rules открыт на запись только для
`srv_settlement` — клиент не может изменить ни свой, ни чужой рейтинг
напрямую.

Квитанции матчей одноразовы: правило вида `!data.exists() && newData.exists()`
запрещает перезапись, поэтому повторная отправка того же начисления —
из-за реконнекта, двойного клика или ретрая — отвергается сервером.

## Firebase Security Rules

Исходник правил: `firebase/database.rules.json`. Они ограничивают доступ по
личности (`auth.uid`), задают форму записей и закрывают серверные пути от
клиента. В репозитории есть тесты правил, которые прогоняются против
настоящего Database Emulator (`npm run test:rules`).

Наличие правил в репозитории **не доказывает**, что именно эта версия
опубликована в проекте Firebase. Workflow публикации в репозитории нет; по
его содержимому нельзя установить, публикуются ли правила каким-либо
внешним механизмом.

## Границы гарантий

Что обеспечено сервером:

- личность игрока проверяется на стороне Worker по подписи Telegram;
- Firebase Auth даёт правилам настоящий `auth.uid`;
- доступ к RTDB ограничен Security Rules;
- рейтинговый результат считается и записывается сервером;
- квитанции матчей одноразовы;
- секретов в репозитории нет.

Чего репозиторий не гарантирует:

- что App Check включён в обязательном режиме в production;
- что ограничение частоты запросов настроено на стороне Cloudflare;
- что опубликованные правила совпадают с версией в репозитории.

Абсолютной защиты от изменённого клиента не обещается: смысл текущей
модели в том, что критичные для рейтинга решения принимает сервер, а не
клиент.

## Что нужно знать, прежде чем что-то менять

### Два времени, и путать их нельзя

    getEstimatedServerNow()   Date.now() + .info/serverTimeOffset
    Date.now()                часы устройства

Все серверные метки — `turnStartedAt`, `absentSince`, `onlineSince`,
`lastSeen`, `createdAt` — пишутся через `ServerValue.TIMESTAMP` и должны
сравниваться ТОЛЬКО с `getEstimatedServerNow()`.

Пока смещение времени неизвестно, `getEstimatedServerNow()` вырождается в
часы телефона. Поэтому любое НЕОБРАТИМОЕ решение о времени обязано быть
fail-closed: не знаем времени — не решаем.

### Присутствие

    online        в игре ли сейчас
    onlineSince   начало текущей непрерывной online-сессии
    absentSince   момент ухода, СЕРВЕРНОЕ время
    lastSeen      биение раз в несколько секунд

`absentSince` пишется только при сворачивании приложения и серверным
`onDisconnect`, и обнуляется любым возвращением.

Два правила, которые легко нарушить:

- при отсутствии связи обычные клиентские записи присутствия НЕ
  выполняются — иначе они копятся в offline-очереди Firebase и после
  реконнекта перезаписывают серверное состояние;
- `onDisconnect` — ОДНОРАЗОВАЯ серверная операция, после каждого
  срабатывания её нужно перевооружать.

### Исходы партии

    обычная победа        winner + winReason
    техническая победа    result{...}, строгая валидация в Rules
    брошенная партия      исхода нет, комната логически мертва

    один offline + один online >= 60 с   -> техническая победа
    оба offline >= 60 с от ухода второго -> брошенная, результата нет

## Развёртывание

Все три части версионируются в репозитории, но ни для одной из них
репозиторий не содержит workflow публикации:

| Часть | Источник в репозитории | Публикация |
|---|---|---|
| Фронтенд | корень | механизм не определяется содержимым репозитория |
| Cloudflare Worker | `worker/` | отдельным действием, workflow в репозитории нет |
| Firebase Rules | `firebase/` | отдельным действием, workflow в репозитории нет |

То есть по содержимому репозитория нельзя установить, как и куда
публикуется каждая часть и совпадает ли развёрнутое состояние с `main`:
отсутствие workflow не исключает внешнюю интеграцию или настройку на
стороне GitHub, Firebase или Cloudflare. Настройки публикации живут вне
репозитория.

Значений секретов (токен бота, ключи сервисного аккаунта) в репозитории
нет — Worker обращается к ним только через переменные окружения.

### Порядок выпуска

1. Патч готовится и проверяется на ЧИСТОМ клоне текущего `main`.
2. `npm run check` и `npm test`, обязательно с проверкой кода возврата.
3. Мутационная проверка: правка ломается нарочно, тесты обязаны падать.
4. Перед push создаются backup-ветка и тег от текущего `main`, и они
   проверяются НА СЕРВЕРЕ через `git ls-remote`.
5. Cache-bust поднимается для изменившегося ресурса: `script.js?v=NNN` и
   `style.css?v=NN` в `index.html`.
6. Только после этого commit и push.

Откат всегда возможен:

    git push --force origin <backup-tag>:main

Backup-ветки и теги не удаляются.

## Известные особенности

- `assets/board.png` — на самом деле JPEG с расширением `.png`. Работает,
  потому что браузеры определяют формат по содержимому.
- Публикация фронтенда, Worker и правил Firebase не автоматизирована в
  репозитории, поэтому расхождение между `main` и развёрнутым состоянием
  возможно и проверяется вручную.
