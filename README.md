# Русские шашки

Telegram Mini App: русские шашки 8×8. Игра с ботом, игра онлайн вдвоём по
ссылке-приглашению, режим зрителя, рейтинг Elo, монеты, статистика. Три
языка: русский, итальянский, английский.

Играть: открыть Mini App в Telegram.

## Стек

    фронтенд     чистый JavaScript, без фреймворков и без сборки
    хостинг      GitHub Pages (ветка main, корень репозитория)
    данные       Firebase Realtime Database, регион europe-west1
    SDK          Firebase 10.7.1 compat
    интеграция   Telegram WebApp API
    тесты        голый Node, без зависимостей

Сборки нет: `script.js` подключается напрямую и выполняется как есть.
`node_modules` в проекте отсутствует и не нужен.

## Запуск проверок

    git clone https://github.com/iliushazb-coder/russkie-shashki.git
    cd russkie-shashki
    npm run check     # node --check script.js
    npm test          # 1032 проверки в 23 сюитах

Установка зависимостей не требуется — `package.json` их не содержит.
Нужен Node 18 или новее.

### Смотрите КОД ВОЗВРАТА, а не только последнюю строку

    npm test; echo $?     # должно быть 0

Сюита, упавшая при загрузке, выводит ноль проверок и молча уменьшает общий
счёт. Раннер это ловит и сообщает отдельным блоком «ПРОБЛЕМНЫЕ СЮИТЫ», но
привычка смотреть на код возврата надёжнее привычки читать итог.

## Что нужно знать, прежде чем что-то менять

### Два времени, и путать их нельзя

    getEstimatedServerNow()   Date.now() + .info/serverTimeOffset
    Date.now()                часы устройства

Все серверные метки — `turnStartedAt`, `absentSince`, `onlineSince`,
`lastSeen`, `createdAt` — пишутся через `ServerValue.TIMESTAMP` и должны
сравниваться ТОЛЬКО с `getEstimatedServerNow()`.

Пока `serverTimeOffsetReady` равно `false`, `getEstimatedServerNow()`
вырождается в часы телефона. Поэтому любое НЕОБРАТИМОЕ решение о времени
обязано быть fail-closed: не знаем времени — не решаем. Так устроены
поражение по времени и разрушительная уборка комнат в лобби.

### Присутствие

    online        в игре ли сейчас
    onlineSince   начало текущей непрерывной online-сессии
    absentSince   момент ухода, СЕРВЕРНОЕ время
    lastSeen      биение каждые 4 секунды

`absentSince` пишется только двумя путями ухода — сворачивание приложения и
серверный `onDisconnect` — и обнуляется любым возвращением. Непрерывность
отсутствия закодирована самим полем, историю хранить не нужно.

Правило: при `isFirebaseConnected !== true` обычные клиентские записи
присутствия НЕ выполняются. Иначе они копятся в offline-очереди Firebase и
после реконнекта перезаписывают серверное состояние.

`onDisconnect` — ОДНОРАЗОВАЯ серверная операция. После каждого срабатывания
её нужно перевооружать.

### Исходы партии

    обычная победа        winner + winReason, серверной валидации НЕТ
    техническая победа    result{...}, строгая валидация в Rules
    брошенная партия      исхода НЕТ, комната логически мертва

Валидация в Rules есть только у ТЕХНИЧЕСКОГО результата: после создания он
неизменяем, `winReason` обязан быть `disconnect`, `decidedAt` не из будущего,
лишние поля запрещены. Обычная победа — по времени, сдаче или доигранной
партии — пишется в `winner`/`winReason` обычной транзакцией и такой проверки
не имеет.

    один offline + один online >= 60 с   -> техническая победа
    оба offline >= 60 с от ухода второго -> брошенная, результата нет никому

### Начисления защищены от ПОВТОРА, но не от подделки

    eloMatches/<matchId>                 запись однократная (правило Rules)
    economy/<uid>/rewardedMatches/<id>   то же для монет

Что это действительно даёт: квитанция матча записывается ровно один раз,
правило `!data.exists() && newData.exists()` запрещает её перезапись, а
дельта рейтинга зажата в диапазон ±32. Повторная отправка того же начисления
— по ошибке, из-за реконнекта или двойного клика — отвергается сервером, а
не клиентом.

Чего это НЕ даёт: защиты от намеренно изменённого клиента. Firebase Auth в
проекте нет, поэтому `auth` в правилах всегда `null`, а `$uid` в пути — это
просто строка, которую прислал клиент. Записать `stats/<чужой uid>` или
`economy/<свой uid>` напрямую, минуя квитанцию, правила не мешают.

Иными словами, квитанция закрывает СЛУЧАЙНОСТЬ, а не злой умысел. Полностью
это закрывается только вместе с аутентификацией — см. «Границы гарантий».

### Вход по ссылке-приглашению

Место чёрных занимается ОДНОЙ корневой транзакцией: проверка комнаты,
запись игрока, статус `active` и `turnStartedAt` — в одном коммите.
Промежуточного состояния на сервере не возникает.

Перед транзакцией на комнату вешается слушатель, который удерживается всё
время транзакции: без него кеш холодный, колбэк получает `null`, и вход
срывается. `applyLocally` выключен, чтобы спекулятивное значение не попадало
в локальный кеш.

Транзакция защищает от ГОНКИ между честными клиентами: сервер сериализует
конкурирующие записи, и место достаётся ровно одному. От клиента, который
пишет в `rooms/<code>` напрямую в обход этой логики, она не защищает —
правило записи на комнату открыто.

## Границы гарантий

Стоит различать три уровня, иначе легко принять одно за другое.

**Обеспечено сервером.** Однократность квитанций `eloMatches` и
`rewardedMatches`. Зажим дельты рейтинга в ±32. Неизменяемость и строгая
форма технического результата. Сериализация конкурирующих транзакций,
благодаря которой место чёрных достаётся одному игроку. Серверные метки
времени через `ServerValue.TIMESTAMP` и `onDisconnect`.

**Обеспечено дисциплиной клиента.** Вооружение `onDisconnect` до объявления
`online`. Отказ писать присутствие без связи. Порядок «прогреть кеш →
транзакция → снять слушатель». Сервер это проверить не может; нарушение
ведёт к fail-closed, а не к ложному исходу.

**Не обеспечено ничем.** Личность отправителя любой записи. Firebase Auth
отсутствует, поэтому правила не знают, кто пишет. Изменённый клиент может
записать чужую статистику, свой баланс монет, произвольную позицию на доске
или удалить чужую комнату. App Check подтверждает, что запрос пришёл из
этого приложения, но не то, кто его отправил.

Это известное и осознанное состояние, а не упущение: закрывается оно
проверкой Telegram `initData` на доверенной стороне с выдачей Custom Token,
и это отдельная работа.

## Как выпускать релиз

Порядок выстрадан и менять его не стоит.

1. Патч готовится и проверяется на ЧИСТОМ клоне текущего `main`.
2. `npm run check` и `npm test`, обязательно с проверкой кода возврата.
3. Каждая сюита прогоняется отдельно — упавшая при загрузке не должна
   потеряться в общем итоге.
4. Мутационная проверка: правка ломается нарочно, тесты обязаны падать.
5. Перед push создаются backup-ветка и тег от текущего `main`, и они
   проверяются НА СЕРВЕРЕ через `git ls-remote`.
6. Cache-bust поднимается для того ресурса, который изменился:
   `script.js?v=NNN` и `style.css?v=NN` в `index.html`.
   Изображения адресуются из CSS и имеют собственный `?v=`.
7. Только после этого commit и push.

Откат всегда возможен:

    git push --force origin <backup-tag>:main

Backup-ветки и теги не удаляются.

## Известные особенности

- `assets/board.png` — на самом деле JPEG с расширением `.png`. Работает,
  потому что браузеры определяют формат по содержимому. Переименование
  потребовало бы правки CSS без реальной пользы.
- Firebase Security Rules хранятся только в Firebase Console и в
  репозитории отсутствуют. Их нельзя ревьюить и откатывать вместе с кодом.
- Firebase Auth в проекте нет: личность берётся из Telegram WebApp, поэтому
  в правилах `auth` всегда `null`.
- Подсистема подбора случайного соперника мертва: `startOnlineSearch` и
  `createOnlineRoom` не вызываются ниоткуда. Вход в онлайн-партию возможен
  только по ссылке-приглашению.
